## 5. 答辩三问（任务书 7.3 的 B 列）

### 5.1 “到位率为什么在 SQL 里算，而不是在 Java 里？”

三个理由，按重要性排：

1. **数据量大、往返多**：240 笔拨付 × 40 个项目，如果在 Java 里“查项目 → 查计划 → 查拨付 → 循环累加”，就是 1 + 40 + 40 次往返；SQL 一次 `GROUP BY` 就出结果，现在是 **4 条 SQL 出 4 类统计**。
2. **口径必须唯一**：到位率的分母是“年度计划”，分子是“拨付”，两者都可能为 NULL / 为 0。SQL 里用 `COALESCE(...,0)` + `CASE WHEN 计划=0 THEN NULL` 统一处理，除零保护写在**一处**；放 Java 里则要保证每个调用方都记得判空。
3. **可解释、可审计**：答辩时把 SQL 贴出来，`plan_total / actual_total / rate_pct` 三个列名就是业务定义，老师一眼能核对。

**加分细节（可以主动讲）**：任务书 2.3 给的标准写法是

```sql
LEFT JOIN t_fund_plan pl ON pl.project_id = p.project_id
LEFT JOIN t_fund_disbursement d ON d.plan_id = pl.plan_id
GROUP BY p.project_id
```

它有一个隐藏坑：一个年度计划有多笔拨付时，`SUM(pl.plan_amount)` 会**按拨付笔数重复计数**，分母翻倍、到位率减半。我实测过：P001 用这种写法算出 **26.26%**，正确值是 **52.52%**（正好差 2 倍，因为这个项目每年有 2 笔拨付）。
所以 `v_fund_rate` 改成“计划、拨付各先聚合成一行再 JOIN”，用子查询把这两个粒度隔开。这是 B 段最值得讲的一个技术细节。

### 5.2 “同项目同月重复报工，怎么防止？”

三层，第一层是根本：

1. **数据库唯一键** `uk_report_project_period (project_id, period_ym)`：并发、重复提交、界面连点，最终都落在这一层；业务代码永远不可能比数据库更可靠。
2. **DAO 把 1062 翻译成人话**：`ReportDao.insertReport()` 捕获 `SQLException.getErrorCode() == 1062`，返回 `Result.fail("该项目 2025-06 已报过进度（唯一约束 uk_report_project_period），请改为修改")`，界面直接弹。
3. **语义区分**：新增（insert）才该报错；修改（update）走 `updateReport()`，报告期不允许改（改期等于换一条记录），所以 upsert 用在这里是错的 —— 这就是 `t_fund_plan` 用 upsert、`t_progress_report` 不用 upsert 的原因。

### 5.3 “预警阈值为什么写在表里，而不是写在代码里？”

1. **阈值是业务参数，不是程序逻辑**：不同国家、不同年份的红线会变；写死在 `if` 里，每改一次就要改代码 + 重新编译 + 重新发版。
2. **规则可组合**：`t_warning_rule` 用“两个条件 + 比较符 + 级别”表达，F1（到位率<60 且 进度<50）、F2（到位率>90 且 进度<40）只是两行数据；新增规则是 `INSERT`，不需要写新方法。
3. **改动可演示**：现场把 F1 的进度阈值 50 改成 65，点刷新，红灯 7 → 10 条；改回来 7 条。这条链路的每一步都能在界面上看到，这也是“加分项”里最好演示的一条。
4. **配合幂等**：`uk_warning_rule_project_period` + `ON DUPLICATE KEY UPDATE`，刷新 10 次和 1 次结果一样；`ACK` 状态不会被覆盖，条件消失自动 `CLOSED` —— 改阈值不会留下一堆僵尸预警。

### 5.4 可能被追问的三个点（先准备好）

| 追问 | 答法 |
| --- | --- |
| “计划外拨付（plan_id 为空）算不算到位率？” | 不算。到位率的口径是“以年度计划为抓手”，计划外拨付不归任何年度计划，所以不计入分子；这类款项在 M4 明细里照常显示。如果要“项目全口径”，把 `v_fund_rate` 的拨付子查询改成按 `project_id` 聚合即可（一行改动）。 |
| “为什么拨付表要有 plan_id，光有 project_id 不行吗？” | 不行。到位率要按**年度**对比计划（Q4-4 和 F1 都依赖年度口径），只有 `project_id` 就退化成“项目全周期”，年度计划对比就没了依据；`plan_id` 让每笔钱有归属，同时允许 NULL 表示计划外。 |
| “EAV 表 `t_report_indicator` 为什么不用固定列？” | 指标会随项目类型增加（培训、采购、安全工时…），固定列要不停 `ALTER TABLE`；EAV 用 `(report_id, indicator_code)` 做主键，加指标只加数据。代价是查单指标要 JOIN + SUM，所以约定 `indicator_val` 存**本期增量**，C 的 M7 承诺比对直接 `SUM` 累计。 |
