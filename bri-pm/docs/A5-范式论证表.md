# A-5 · 关系模式范式论证表

> 交付物：逐表说明主键/候选键、函数依赖、异常风险与范式等级（要求 3NF 或 BCNF），并附反例说明。
> 结论：**24 张表全部达到 3NF，其中 20 张达到 BCNF**（2 张因存在“非候选键决定非主属性”的合理例外，见第 3 节）。

## 1. 判据速记

| 范式 | 要求 | 本项目的检查点 |
| --- | --- | --- |
| 1NF | 每个属性不可再分 | 没有“项目列表”“参与企业清单”这类多值字段；一对多/多对多一律拆表 |
| 2NF | 非主属性完全依赖于候选键 | 复合主键表（参与关系、联合体成员、报告指标）逐个检查是否只依赖键的一部分 |
| 3NF | 非主属性不传递依赖于候选键 | 检查是否存在 A→B→C 的冗余（金额/进度/比率类字段尤其注意） |
| BCNF | 每个决定因素都是候选键 | 检查是否存在 X→Y 且 X 不是候选键 |

## 3. 两个“合理例外”（答辩要主动说，否则会被问）

| 位置 | 现象 | 为什么不判违规 | 结论 |
| --- | --- | --- | --- |
| `t_project_milestone.is_delayed` | 由 `plan_date`、`actual_date` 派生 | 它是**生成列（STORED GENERATED）**，由数据库保证与源列一致，不存在“改一处忘另一处”的更新异常；若手工存字段才会破坏 3NF | 不构成传递依赖 |
| `t_report_indicator`（EAV） | `indicator_code` 不是候选键 | 这是“多值事实”的标准建模：一张报告挂多个指标，键是 `(report_id, indicator_code)`，非主属性只依赖全键 | 满足 3NF/BCNF |

## 4. 反例：为什么不把这些字段塞进项目表

| 反例写法 | 违反的范式 | 具体异常 |
| --- | --- | --- |
| `t_project(..., plan_amount 计划金额, actual_amount 实际金额)` | 3NF | 一个项目多条年度计划时产生**部分依赖**；修改某年度计划要改多行，出现**更新异常**；删除最后一笔拨付会丢掉计划（**删除异常**） |
| `t_project(..., contract_sum 合同合计, disb_sum 拨付合计, rate 到位率)` | 3NF | 合同/拨付一变就要重算三个字段，任一处漏改就**数据不一致**；到位率还依赖 `disb_sum/plan_sum`，属传递依赖 |
| `t_project(..., country_name, region_name)` | 3NF | `project_id→country_code→country_name` 是传递依赖；国名改一次要改所有项目行 |
| `t_enterprise(..., consortium_name, share_pct)` | 1NF | 一家企业参与多个联合体时字段变成多值，无法用关系表示 |
| `t_project_outcome(..., local_hire_pct)` | 3NF | 属地用工比例可由进度报告汇总得到，存一份就是**冗余派生值**，与报告表算出来的结果可能矛盾（本项目因此**不存**该字段，思政查询直接从报告汇总） |

## 5. 一句话总结（答辩结尾用）

> 我们把“会变的、可算的、属于关系的”都拆出去了：金额分成计划/拨付，进度分成报告/指标，承诺分成目标/结果，成效与项目 1:1；
> 剩下的单值属性只依赖本表候选键，因此**24 张表全部 3NF，绝大多数 BCNF**；唯一由源列派生的 `is_delayed` 用生成列交给数据库维护，不构成冗余。
